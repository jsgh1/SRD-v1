# Cliente Android de SRD

## Variante Expo Go para la exposición

`apps/mobile-expo` es una adaptación separada de las pantallas de esta app para ejecutarlas en Expo Go por USB, sin compilar un APK ni arrancar el emulador. La guía exacta está en [apps/mobile-expo/README.md](../apps/mobile-expo/README.md). Usa SDK 57, React Native 0.86.3 y `expo-secure-store` para recordar solo servidor y código de junta. El inicio muestra resumen y tarjetas, con navegación inferior que no aparece cuando quedan términos por aceptar; el perfil identifica cuenta y junta, y Agenda y Avisos presentan estados vacíos legibles. Al volver al inicio se recargan los indicadores. El botón Atrás de Android vuelve desde las pantallas internas, sin pasar por alto términos pendientes o cambios de junta sin confirmar. `npx tsc --noEmit`, lint, exportación del bundle Android y `expo-doctor` aprobaron el 8 de octubre de 2026. El manifiesto de Expo respondió por IPv4 local. Un recorrido visual con datos sintéticos verificó login, MFA, resumen y navegación a 320 px. `Prepare-ExpoDemo.ps1` inició la pila reducida y `mobile-expo-api.spec.mjs` aprobó contra el gateway real login, MFA por Mailpit, resumen, personas, agenda, avisos y cierre de sesión. **En un teléfono Android físico** se comprobó por USB el login con MFA, Inicio, Personas con tres registros ficticios, Agenda con dos eventos, la apertura de Avisos y Perfil, y la persistencia de la sesión tras salir y reabrir Expo Go. El botón Atrás y las escrituras desde ese teléfono aún están pendientes. La app nativa descrita abajo sigue independiente.

Con una sesión iniciada, **Cambiar de junta** pide el código de destino, carga sus términos vigentes y exige aceptación expresa antes de solicitar el cambio. Al concluir, consulta `/me` para confirmar la junta activa, limpia los datos en memoria de la anterior y carga un resumen nuevo. Si la respuesta del cambio se pierde, bloquea otro envío hasta **Comprobar junta activa**. Cuando cambian los términos de la junta actual, bloquea el resumen hasta aceptarlos o cerrar sesión. El servidor sigue decidiendo si la cuenta tiene acceso a la junta destino. Este flujo pasó pruebas JavaScript y compilación Android; falta recorrido nativo entre dos juntas.

El primer cliente React Native está en `apps/mobile`. Es una aplicación Android nativa, sin WebView, que abre directamente en **Iniciar sesión**. En el mismo flujo solicita la dirección del servidor y el código de junta, consulta la junta, muestra sus términos, solicita correo y contraseña, verifica el código de seis dígitos y presenta cuatro indicadores del resumen. Permite mostrar u ocultar la contraseña, solicitar instrucciones de recuperación, reenviar o cancelar la verificación y cerrar sesión. Incorpora además búsqueda de personas por nombre o documento, lista paginada por el servidor, lectura explícita de una ficha y consulta exacta por tipo y número de documento. Esta última conserva los ceros iniciales y diferencia entre ausencia de resultado y fallo de consulta. La ficha muestra solo campos seleccionados de la respuesta autorizada; no presenta la nota interna.

Los roles Superadministrador, Administrador y Registrador tienen un primer formulario de **alta pendiente** con tipo/número de documento, nombres, apellidos opcionales y fundamento/finalidad de la autorización de tratamiento. El cliente obtiene las versiones vigentes de campos y cargos antes de enviar el alta; el servidor vuelve a validar junta, rol, unicidad y datos. Tras confirmar el guardado, una pantalla separada permite abrir la ficha sin volver a enviar el formulario. **Completar o editar el registro y adjuntar fotografías** sigue siendo una tarea de web/Windows mientras se desarrolla esa parte móvil. Si se pierde la respuesta de red durante el envío, la app indica consultar el documento antes de repetir el alta y no reintenta automáticamente el POST: el backend rechaza duplicados, pero el cliente no puede confirmar por sí solo el resultado.

La **agenda móvil inicial** consulta una semana a la vez, permite avanzar o retroceder, actualizar y abrir el detalle de un evento autorizado. Muestra tipo, estado, lugar, descripción y participantes. Convierte los instantes del servidor a `America/Bogota` para las horas visibles; el rango de consulta se expresa como fechas de esa zona. **Mis invitaciones** lista las participaciones futuras, permite paginar, abrir el evento y aceptar o rechazar. Rechazar requiere una confirmación en pantalla; la API usa la versión de la respuesta para detectar cambios concurrentes. Si falla la recarga después de una respuesta confirmada, la app conserva el estado confirmado y avisa que la lista necesita actualizarse. Crear, editar y cancelar eventos todavía se gestiona desde web/Windows.

**Notificaciones** ofrece una bandeja personal paginada con contador de avisos sin leer. Permite actualizarla manualmente, marcar un aviso como leído, descartarlo tras confirmación y abrir el evento autorizado asociado. Los avisos de Chat indican que la conversación se consulta por ahora en web/Windows. Lectura y descarte pasan por la autorización del servidor para el usuario y la junta activos; si se pierde la respuesta, el cliente intenta recargar la bandeja y no repite automáticamente la escritura. No hay sondeo, push ni avisos en segundo plano en Android.

Desde la bandeja, **Preferencias de avisos** consulta y guarda para la cuenta y junta activas las categorías opcionales de cambios de eventos, recordatorios y Chat, más el horario de silencio. Invitaciones y cancelaciones no se desactivan. Las horas se escriben en formato `HH:mm`, pueden cruzar medianoche y deben ser diferentes; el cliente valida ambos extremos antes de enviar un `PUT` con CSRF. La API devuelve los valores guardados. Si se pierde la respuesta, la app impide repetir el guardado en esa pantalla y exige volver a abrirla para consultar el estado. El horario oculta el distintivo de la campana **web** y conserva los avisos; Android todavía no tiene distintivo ni push, por lo que su efecto local no está implementado.

**Mi perfil** permite consultar el nombre y correo de acceso y cambiar el nombre y la preferencia de presencia (en línea, ausente, no molestar o invisible). Antes de editar consulta el perfil vigente; tras guardar vuelve a consultarlo. Conserva el tema que ya tiene la cuenta, porque todavía no hay selector de tema en Android. El correo y otras preferencias continúan en web/Windows. Si se pierde la respuesta de guardado, no repite la escritura y pide reabrir el perfil para comprobar el resultado.

Al abrir Android, el cliente recuerda **solo la dirección del servidor y el código de junta** en el almacenamiento privado de la app. Consulta de nuevo la junta y `/me`: si la cookie del servidor sigue vigente, abre el resumen; si la sesión terminó, muestra el login de esa junta. No guarda contraseñas, códigos MFA, cookies ni tokens en ese almacenamiento. Cambiar junta o servidor desde el login borra la conexión recordada; cambiar de junta durante una sesión actualiza el código recordado tras comprobar `/me`; cerrar sesión revoca la sesión del servidor. Ante un fallo de red durante esta comprobación, ofrece reintentar o cambiar servidor sin asumir que la sesión expiró.

Cuando la app vuelve del segundo plano con una cuenta abierta, consulta `/me` otra vez. Durante la comprobación oculta el contenido autenticado. Si el servidor indica 401, limpia ese contenido y vuelve al login de la junta. Si falla la conexión, mantiene el contenido oculto y ofrece **Reintentar**; solo lo muestra al confirmar de nuevo la sesión. El servidor sigue autorizando cada acción. No hay sondeo en segundo plano ni aviso inmediato mientras la app permanece abierta sin interacción.

## Estado comprobado

- React Native 0.87.1 y dependencias bloqueadas en `package-lock.json`.
- `npm test`: treinta y siete pruebas aprobadas. `npx tsc --noEmit` y `npm run lint -- --quiet`: aprobados.
- Metro generó el bundle Android actualizado en `.local/mobile/index.android.bundle`. La depuración normal consume JavaScript desde Metro. Para probar con menos memoria, el APK actual se compiló con `-PsrdEmbedDebugJs=true`: incorpora el JavaScript de desarrollo y arranca sin Metro.
- `gradlew :app:assembleDebug --no-daemon --max-workers=2 --no-parallel -PreactNativeArchitectures=x86_64 -PsrdEmbedDebugJs=true` aprobó. El APK x86_64 actual está en `apps/mobile/android/app/build/outputs/apk/debug/app-debug.apk` y en `.local/mobile/app-debug-embedded.apk` (42.466.584 bytes, SHA-256 `B18382F460DD3AE3BB79D3C3E3BE4EAD4F91F6FFD1FF83AA27922D86A51B7142`). Es solo para pruebas locales: conserva `__DEV__` y permite el gateway HTTP del emulador. Los cambios recientes de comprobación al volver del segundo plano y cambio de junta aún no tienen recorrido nativo.
- En el emulador Android 15, una cuenta sintética completó junta, login, MFA por Mailpit local, resumen y bandeja vacía. **Mi perfil** cargó, guardó nombre y presencia, volvió a leerlos y permitió restaurar los valores originales. **Preferencias de avisos** cargó, guardó categoría desactivada y horario 22:00–07:00, persistió al reabrir y permitió restaurar categorías y horario. La sesión se cerró desde la app. Esto comprueba escrituras con cookie y CSRF en estas dos pantallas.
- En el recorrido nativo anterior se comprobaron también lista vacía de personas y agenda semanal vacía. El nuevo recorrido confirmó que una sesión activa volvió al resumen después de `am force-stop` y reapertura, y que una sesión cerrada volvió al login con la junta recordada. Siguen sin probarse en Android el alta de persona, invitaciones con datos, lectura/descarte de avisos, caducidad automática y revocación desde otro dispositivo, teléfono físico y compilación de publicación.

El cliente usa las rutas existentes del gateway y `fetch` con `credentials: 'include'`, sin guardar contraseñas, códigos, cookies o tokens en el almacenamiento de la app. [React Native advierte que la autenticación basada en cookies es inestable](https://reactnative.dev/docs/network). El recorrido local demuestra persistencia después de un cierre forzado en **este emulador**. Dos sesiones sintéticas comprobaron revocación real del servidor y una prueba JavaScript comprobó la reacción de Android al regresar del segundo plano; falta ese recorrido nativo, además de otros dispositivos, caducidad por tiempo y autenticación de producción. El diseño de autenticación nativa debe resolver emisión y custodia de credenciales, renovación y cierre de sesión centralizado antes de considerar terminado RF-052.

## Herramientas instaladas para esta prueba

En este equipo se instalaron en `G:\SRD-Android-tools` JDK 17, Android SDK, Platform-Tools, Build-Tools, NDK, CMake y el emulador; el dispositivo virtual `SRD_API35` también guarda sus datos en G:. Se configuraron `JAVA_HOME`, `ANDROID_HOME`, `ANDROID_AVD_HOME` y `GRADLE_USER_HOME` **solo en los procesos de prueba**, sin cambiar variables globales. Android Studio gráfico no fue necesario. El APK de desarrollo está dentro del proyecto, en la ruta indicada arriba; no es un instalador oficial ni está firmado para distribución.

Con 16 GB de RAM, Gradle, Docker, Metro y emulador abiertos a la vez provocaron presión de memoria y un cierre de VS Code. La compilación pasó con dos trabajadores y el emulador cerrado. El AVD propio de SRD se ajustó a 1536 MB y dos núcleos; su configuración anterior quedó respaldada en `.local/mobile/SRD_API35-config-before-lite.ini`. El APK autónomo evitó ejecutar Metro durante la prueba; se arrancaron solo los servicios Docker necesarios. Al terminar se restauró el tamaño de pantalla, se detuvieron los contenedores SRD, el emulador y Docker Desktop. Para volver al entorno completo, seguir `README.md`.

La recuperación solicita al gateway el envío de instrucciones con una respuesta genérica para proteger la existencia de cuentas. El enlace del correo termina en el restablecimiento web ya existente; aún no hay enlace profundo nativo ni captura de su secreto en Android.

## Desarrollo en otra máquina

1. Levantar SRD según `README.md` y comprobar el gateway local.
2. Instalar Android Studio, Android SDK compatible con la plantilla y JDK 17 según la [guía oficial de entorno de React Native](https://reactnative.dev/docs/set-up-your-environment); configurar las variables de Android únicamente en el entorno de esa máquina.
3. En `apps/mobile`, ejecutar `npm ci` y `npm run android` con un emulador Android abierto. Para Metro por separado: `npm start`.
4. En el emulador, el servidor local predefinido en compilación de desarrollo es `http://10.0.2.2:8080`. Ingresar el código real de la junta de prueba de esa instalación. Un dispositivo físico necesita una dirección HTTPS accesible desde su red.

La compilación de desarrollo permite HTTP para el gateway local del emulador; el cliente acepta HTTP solamente para direcciones locales en modo desarrollo. Release exige HTTPS y Android deshabilita tráfico claro. La plantilla no contiene firma de publicación; no se ha generado ni distribuido instalador oficial Android.

Quedan por implementar y validar en Android: autenticación nativa estable en más escenarios y dispositivos, restablecimiento de contraseña dentro de la app, formulario completo/edición de registros y fotografías, creación/edición/cancelación de eventos, aplicación móvil del horario de silencio, entrega push de notificaciones, chat/voz, edición del correo y del tema, y accesibilidad/recorridos físicos. El recorrido de perfil y preferencias fue una prueba funcional sintética, no aceptación integral. El código iOS generado por la plantilla no forma parte del alcance ni se ha probado.
